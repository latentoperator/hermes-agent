## Root-cause claim verification

The claim: unsynchronized concurrent first-use of `_get_client()` can orphan
aiohttp-backed Hindsight clients, producing "Unclosed client session" /
"Unclosed connector" warnings.

**Verified true.** `_get_client()` is reachable from at least three thread
contexts:

1. Prefetch thread — `queue_prefetch()` spawns `hindsight-prefetch` (line 1526),
   which calls `_run_hindsight_operation` → `_get_client()`.
2. Retain writer thread — `_writer_loop()` drains retain jobs that call
   `_run_hindsight_operation` → `_get_client()`.
3. Main agent thread — memory tool calls and the embedded daemon-start thread
   (line 1432).

Before the fix, all three paths hit `if self._client is None:` with no lock.
Two concurrent first-use callers could each pass the check, construct a
client, and assign to `self._client`. The losing assignment overwrote the
winner, orphaning one `Hindsight` / `HindsightEmbedded` instance and its
aiohttp `ClientSession` + `TCPConnector` until GC.

## Fix assessment

The fix implements standard double-checked locking:

```python
def _get_client(self):
    client = self._client           # fast path: unlocked read
    if client is not None:
        return client
    with self._client_lock:
        if self._client is None:    # double-check under lock
            self._client = self._create_client()
        return self._client
```

- **Correct pattern.** The local `client = self._client` snapshot avoids
  returning a reference that another thread might be mid-construction on.
  Under CPython's GIL, the attribute read/write is atomic; the double-check
  ensures only one construction per provider lifetime.
- **Clean extraction.** `_create_client()` is a pure factory — it reads config
  and returns a client without touching `self._client`. This keeps the locked
  section minimal (no I/O, no `ensure()` under the lock for cloud mode, though
  `_check_local_runtime()` + `lazy_ensure()` do run under the lock for
  embedded mode — acceptable since they're fast local checks).
- **`threading` already imported** at module level (line 41). No new
  dependency.

## Shutdown / thread-safety interplay

The shutdown path (`shutdown()`, line 1926+) does NOT acquire `_client_lock`
when closing `self._client`. This is acceptable because:

1. `shutdown()` sets `_shutting_down` and joins the prefetch thread (5s timeout)
   and writer thread (10s timeout) BEFORE touching `self._client`.
2. Both worker threads check `_shutting_down.is_set()` before each iteration,
   so they stop requesting new clients once shutdown is in flight.
3. The close at line 1945-1969 handles embedded vs cloud cleanup correctly.

There is a narrow theoretical race: if a worker thread is mid-`_get_client()`
(inside the lock, constructing a client) exactly when `shutdown()` joins and
times out, shutdown could close the old client while a new one is being built.
This is pre-existing behavior — the PR neither introduces nor worsens it — and
the `_shutting_down` gate + join timeouts bound the window in practice.

**Observation (non-blocking):** Line 1182 (`self._client = client` in the
embedded retry path) is now redundant — `_get_client()` already sets
`self._client` under the lock. Harmless; left over from the pre-refactor code.
